# kama gaps and bugs

The running list of what kyoten hits in [kama](../../kama). Two kinds of entry:

- **BUG**: kama does something wrong. Each entry carries a repro, and these should be fixed upstream.
- **GAP**: kama does not do something yet. Some gaps belong upstream; some are ours to build.

**Status values:** `open` · `worked-around` (we ship a local fix; upstream is still open) · `not kama's` ·
`wontfix`. There is no `fixed`: a fixed entry is deleted from this file, and the commit that deletes it says
which kama version closed it.

**Verify by running a repro, never by reading a version string.** Each entry names the kama version it was
reproduced on.

| KY-2 | GAP | open | **No installable Android app.** *(Narrowed 2026-11-04: the Android target this entry first asked for shipped as kama KR-280 in 0.9.830.)* Re-checked here on 0.9.839: `kama build hello.kama --target aarch64-linux-android29` finds NDK r30 through `$ANDROID_NDK_HOME` and writes *"ELF 64-bit LSB pie executable, ARM aarch64 … for Android 29, built by NDK r30"*. kama's `docs/targets.md` says such a program runs under `adb shell`, which was not tried from here. `--target ANDROID` and an unversioned `aarch64-linux-android` are refused by design, the second naming the fix (*"names no Android API level … write `aarch64-linux-android29`"*). **What Meta Quest's native route still needs is an app the launcher starts:** an APK whose `NativeActivity` loads the `.so`, signed, with Meta's manifest entries, and `main` kept as the entry with the activity's lifecycle delivered as events. That is kama's KR-283, claimed by its Windows machine (this one) and ruled 2026-11-02; its next step is a ruling on `kama.json`'s shape (kama `6cac55c7`, 2026-11-03). kyoten's VR needs it ([design/xr.md](design/xr.md) question 4; KYR-32). Repro: a `println` hello built for `aarch64-linux-android29`; no APK step exists to try. Reproduced on 0.9.839, Windows 11, msys2 UCRT64, NDK `30.0.16248370`. Filed upstream as kama KR-280 (shipped) and KR-283 (open). |
| KY-3 | GAP | open | **No iOS target.** `--target IOS` is refused as `ANDROID` is. `aarch64-ios-none` transpiles and derives `OS_IOS`, so std's `OS_MACOS` declarations (`std::net`'s `ListenOptions`, for one) fall to their generic branch, and since a triple's components are the only flags, nothing names what macOS and iOS share. **Apple's own spelling, `arm64-apple-ios`, derives `ARCH_ARM64` and `OS_APPLE`**: neither `ARCH_AARCH64` nor `OS_IOS` holds, a trap for a triple copied from Xcode. A shippable build also needs Apple's clang and the iOS SDK (so a Mac), an app entered through `UIApplicationMain` with frames from `CADisplayLink` (the OS owns the loop, as the browser does on wasm), and a signed `.app` with a provisioning profile. `dlopen` is barred there, so kama's planned hot reload is desktop-only (kama `docs/ROADMAP_DETAIL.md` § the hot-reload library). Reproduced on 0.9.803, Windows 11, by transpiling only; a build needs a Mac. Filed upstream as kama KR-281, with the spelling trap as KR-279, which also covers `aarch64-apple-darwin` on macOS (`cd549777`). KR-281 is done on a Mac, after KR-279, which kama's Windows machine claimed on 2026-11-02 (`62322f93`). **The spelling trap is fixed** (KR-279, 0.9.807; re-checked here on 0.9.810): `--target arm64-apple-ios` is refused with *"target triple 'arm64-apple-ios' has a vendor (`apple`) in the middle, as clang spells it; kama's triple is <arch>-<os>-<abi> — write `aarch64-ios-none`"*, and `aarch64-ios-none` still transpiles. The iOS target itself (KR-281) is still open. **Re-checked on 0.9.839** (2026-11-04): unchanged. `--target IOS` is refused, `aarch64-ios-none` transpiles, and KR-281 is open and unclaimed. |
| KY-5 | GAP | open | **Two `spawn`s in one `scope` cannot share a read-only borrow.** `fn void reader(const ref DynamicArray<int32> c)`, spawned twice as `spawn reader(c: ref c)`, is refused: *"two children in this `scope` borrow overlapping places (`c` and `c`) — a shared mutable borrow across tasks would race"*, with a second error calling the second spawn a write. One such spawn builds and runs. `c: c` is refused ("pass … by `ref`"), and `c: const ref c` does not parse. This is what SPEC § Structured concurrency states ("so is the same local twice", `docs/SPEC.md:7356`), so it is a gap, not a bug; `parallel_for (const ref T e in coll)` is the only read-only sharing today. **Why kyoten cares:** several systems reading one component store at once is where Bevy, Unity's jobs and Unreal's Mass get much of their parallelism ([research/component-models.md](research/component-models.md) § 4, probe 4). Without it, each parallel system in a phase must own a disjoint store. Reproduced on 0.9.803, Windows 11, msys2 UCRT64. Filed upstream as kama KR-288, unscoped: scheduled, design first, on what makes a type safe to read from several tasks (`1c1f165f`, 2026-11-02). **Re-checked on 0.9.839** (2026-11-04): still refused with the same overlap error, while one spawn alone checks. KR-288 is open. |
| KY-6 | GAP | open | **A `--release --target WASM` build does not run Closure.** kama's wasm release passes `-Oz` and section GC (`src/kama.driver.cpp:13766-13770` on 0.9.839) but never `--closure=1`, while emdawnwebgpu's README says *"In all cases, it is important to enable Closure to reduce code size in release"*. On kama's `examples/webgpu` triangle (brotli -q 11), `--closure=1` takes the JS from 11,768 to 7,117 B and the whole build from 22,518 to 17,867 B, and the triangle still draws the same pixels ([research/web-baseline.md](research/web-baseline.md)). A project can opt in today with an `ldflags` entry gated to `ARCH_WASM32`, so this is about the default, and about documenting that Closure renames a `jsLibraries` file's unquoted property names. Reproduced on 0.9.803 with emscripten 6.0.13, Windows 11. Filed upstream as kama KR-289, queued and unclaimed; the project-level `ldflags` opt-in stays the workaround (`1c1f165f`, 2026-11-02). **Re-checked on 0.9.839** (2026-11-04), by reading the driver: still no `--closure`. KR-289 is queued and unclaimed. |
| KY-9 | GAP | open | **A general-purpose graphics library, `@kama/graphics`, as a first-party package, where kama's roadmap keeps the renderer in the engine.** The owner wants kyoten's Three.js-shaped graphics library to be a `@kama` package (2026-11-03): scene, meshes, materials, lights, a camera and loaders, on `@kama/gpu`, naming no engine concept. In the owner's words: "If it can exist outside of kyoten it probably will be in kama for now. I can see the light weight graphics library used by just about anything and doesn't need to be game engine / simulation or even real time" ([design/architecture.md](design/architecture.md) § Decided, question 7). **What kama says today:** its § 8 engine track lists "scene/material" as a tier of the engine and says "the engine *spine* (buffer/pipeline/binding libraries, renderer) is the engine product" (`docs/ROADMAP_DETAIL.md:2843-2844`). With KR-25 and KR-26 claimed: "What stays in the engine is what the designs already leave out of them: frame pacing, the renderer and the XR swapchain" (`:2862-2863`). `@kama/gpu`'s scope keeps buffers, bindings and pipelines "*as an engine renderer*" out (`:2900-2901`). **Why the owner reads it as first-party:** kama's own rule is "a first-party package if it stands alone" (`:2865-2867`). GPU and window passed that rule because "a tool or an editor needs both as much as a game does", and the same holds here. cosmic-forge's viewer (its `render` package, which forge shaped as a renderer package for kyoten), kyoten's editor and the owner's non-game Three.js-style products would use it, and none needs a frame loop or a simulation. **The ask, for kama to rule:** (1) accept the library as a first-party package beside `@kama/gpu`, amending § 8's renderer line, with a row as KR-25 and KR-26 have; (2) say whether its design lives in § 8 as theirs do, or in its own repository; (3) whether kyoten builds it as its first consumer, as it does KR-25 and KR-26 (kyoten's KYR-9). **Its name is `@kama/graphics`** (the owner, 2026-11-03), imported as `graphics` (`graphics::Mesh`); a path package of that name installs and runs on 0.9.823. It avoids the first-party names in use (`gpu`, `window`, `http`, `ui`, `tls`, `sodium`, `postgres`, `redis`), the peers' own packages (`gfx` in FFD and the-mallow-man, `render` in cosmic-forge, `view` in FFD) and kyoten's `render` module, and it says nothing about games or real time. **Repro:** none applies, as nothing is broken. On kama `9f601224` (0.9.831 source; 0.9.823 built here), no `@kama` package or KR row covers a scene, mesh or material library. Not yet filed upstream: for kama to rule. |
| KY-10 | BUG | open | **kama's agent guidance says to `cast<int32>` for `main`'s exit code, and `main` cannot return an `int32`.** `AGENTS.md`, as `kama agents print` writes it on 0.9.839 (kama `agents/AGENTS.md:85-86`), says to *"reach for `cast<int32>(…)` only where the value genuinely leaves the size domain, such as `main`'s exit code"*. Since 0.9.684 (kama `d0ffc06e`), `fn int32 main()` is refused: *"`main` returns the exit status in the platform's own type — write `fn uint8 main()` (the one byte Linux and macOS keep; `fn uint32 main()` on Windows) … narrow a computed status with `cast<uint8>(…)`, which traps if it does not fit, or `truncate<uint8>(…)` to keep its low bits"*. An agent that follows the guidance writes an exit path the compiler refuses. It is one clause, but it is in the file every kama project's agent reads first. Repro: `fn int32 main() { isize n = 3; return cast<int32>(n); }`, then `kama check`. Reproduced on 0.9.839, Windows 11, msys2 UCRT64. Not yet filed upstream. |
| KY-11 | GAP | open | **A module cannot say which sibling modules it may import, so a rule between public modules cannot be the compiler's.** kyoten's rule ([design/architecture.md](design/architecture.md) § Decided, 2026-11-04) is that an engine system never imports another system. `visibility` is a list on the *imported* module, and a module a consumer imports must be `public`, which opens it to every sibling as well. So nothing in `kama.json` lets a game import `audio` while refusing `render` the same import. Repro: a library `eng` with modules `audio`, `render` and `frame`, and a game that depends on it by path and imports `eng::audio::play`. With `audio` `public`, `render`'s `import { eng::audio::play };` checks OK. With `"visibility": ["frame"]`, `render` is refused (*"module `eng::audio` is not visible from `eng::render` — its `visibility` in `kama.json` does not name this module"*), and so is the game (*"module `eng::audio` is not visible from `game`"*). **The ask:** a list on the importing node, naming the modules of its own package that it may import, so that `kama check` and the editor refuse a forbidden edge. One shape would be `"render": { "visibility": "public", "imports": ["frame", "world"] }`, but the shape is kama's. kyoten holds the rule meanwhile with a check in `tools/` (ROADMAP KYR-53). Reproduced on 0.9.840 (`0.9.840+g6cac55c7`), Windows 11, msys2 UCRT64. Not yet filed upstream. |
