# kama gaps and bugs

The running list of what kyoten hits in [kama](../../kama). Two kinds of entry:

- **BUG**: kama does something wrong. Each entry carries a repro, and these should be fixed upstream.
- **GAP**: kama does not do something yet. Some gaps belong upstream; some are ours to build.

**Status values:** `open` · `worked-around` (we ship a local fix; upstream is still open) · `not kama's` ·
`wontfix`. There is no `fixed`: a fixed entry is deleted from this file, and the commit that deletes it says
which kama version closed it.

**Verify by running a repro, never by reading a version string.** Each entry names the kama version it was
reproduced on.

| KY-3 | GAP | open | **No iOS target.** `--target IOS` is refused as `ANDROID` is. `aarch64-ios-none` transpiles and derives `OS_IOS`, so std's `OS_MACOS` declarations (`std::net`'s `ListenOptions`, for one) fall to their generic branch, and since a triple's components are the only flags, nothing names what macOS and iOS share. **Apple's own spelling, `arm64-apple-ios`, derives `ARCH_ARM64` and `OS_APPLE`**: neither `ARCH_AARCH64` nor `OS_IOS` holds, a trap for a triple copied from Xcode. A shippable build also needs Apple's clang and the iOS SDK (so a Mac), an app entered through `UIApplicationMain` with frames from `CADisplayLink` (the OS owns the loop, as the browser does on wasm), and a signed `.app` with a provisioning profile. `dlopen` is barred there, so kama's planned hot reload is desktop-only (kama `docs/ROADMAP_DETAIL.md` § the hot-reload library). Reproduced on 0.9.803, Windows 11, by transpiling only; a build needs a Mac. Filed upstream as kama KR-281, with the spelling trap as KR-279, which also covers `aarch64-apple-darwin` on macOS (`cd549777`). KR-281 is done on a Mac, after KR-279, which kama's Windows machine claimed on 2026-11-02 (`62322f93`). **The spelling trap is fixed** (KR-279, 0.9.807; re-checked here on 0.9.810): `--target arm64-apple-ios` is refused with *"target triple 'arm64-apple-ios' has a vendor (`apple`) in the middle, as clang spells it; kama's triple is <arch>-<os>-<abi> — write `aarch64-ios-none`"*, and `aarch64-ios-none` still transpiles. The iOS target itself (KR-281) is still open. **Re-checked on 0.9.839** (2026-11-04): unchanged. `--target IOS` is refused, `aarch64-ios-none` transpiles, and KR-281 is open and unclaimed. |
| KY-5 | GAP | open | **Two `spawn`s in one `scope` cannot share a read-only borrow.** `fn void reader(const ref DynamicArray<int32> c)`, spawned twice as `spawn reader(c: ref c)`, is refused: *"two children in this `scope` borrow overlapping places (`c` and `c`) — a shared mutable borrow across tasks would race"*, with a second error calling the second spawn a write. One such spawn builds and runs. `c: c` is refused ("pass … by `ref`"), and `c: const ref c` does not parse. This is what SPEC § Structured concurrency states ("so is the same local twice", `docs/SPEC.md:7356`), so it is a gap, not a bug; `parallel_for (const ref T e in coll)` is the only read-only sharing today. **Why kyoten cares:** several systems reading one component store at once is where Bevy, Unity's jobs and Unreal's Mass get much of their parallelism ([research/component-models.md](research/component-models.md) § 4, probe 4). Without it, each parallel system in a phase must own a disjoint store. Reproduced on 0.9.803, Windows 11, msys2 UCRT64. Filed upstream as kama KR-288, unscoped: scheduled, design first, on what makes a type safe to read from several tasks (`1c1f165f`, 2026-11-02). **Re-checked on 0.9.839** (2026-11-04): still refused with the same overlap error, while one spawn alone checks. KR-288 is open. **Re-checked on 0.9.845** (2026-11-04), as two `const ref` readers of a world's field from the world's own method: still refused, and the second error still calls a read a write (*"the child reads it, so writing it here races with the child"*). **Priority (the owner, 2026-11-04):** raise it with KY-12. kyoten's parallel work is proven by the compiler ([design/frame-phases.md](design/frame-phases.md) § Decided, question 6), and this is the largest share of the parallelism that proof refuses today. For the owner to relay. |

A project can opt in today with an `ldflags` entry gated to `ARCH_WASM32`, so this is about the default, and about documenting that Closure renames a `jsLibraries` file's unquoted property names. Reproduced on 0.9.803 with emscripten 6.0.13, Windows 11. Filed upstream as kama KR-289, queued and unclaimed; the project-level `ldflags` opt-in stays the workaround (`1c1f165f`, 2026-11-02). **Re-checked on 0.9.839** (2026-11-04), by reading the driver: still no `--closure`. | KY-9 | GAP | open | **A general-purpose graphics library, `@kama/graphics`, as a first-party package, where kama's roadmap keeps the renderer in the engine.** The owner wants kyoten's Three.js-shaped graphics library to be a `@kama` package (2026-11-03): scene, meshes, materials, lights, a camera and loaders, on `@kama/gpu`, naming no engine concept. In the owner's words: "If it can exist outside of kyoten it probably will be in kama for now. I can see the light weight graphics library used by just about anything and doesn't need to be game engine / simulation or even real time" ([design/architecture.md](design/architecture.md) § Decided, question 7). **What kama says today:** its § 8 engine track lists "scene/material" as a tier of the engine and says "the engine *spine* (buffer/pipeline/binding libraries, renderer) is the engine product" (`docs/ROADMAP_DETAIL.md:2843-2844`). With KR-25 and KR-26 claimed: "What stays in the engine is what the designs already leave out of them: frame pacing, the renderer and the XR swapchain" (`:2862-2863`). `@kama/gpu`'s scope keeps buffers, bindings and pipelines "*as an engine renderer*" out (`:2900-2901`). **Why the owner reads it as first-party:** kama's own rule is "a first-party package if it stands alone" (`:2865-2867`). GPU and window passed that rule because "a tool or an editor needs both as much as a game does", and the same holds here. cosmic-forge's viewer (its `render` package, which forge shaped as a renderer package for kyoten), kyoten's editor and the owner's non-game Three.js-style products would use it, and none needs a frame loop or a simulation. **The ask, for kama to rule:** (1) accept the library as a first-party package beside `@kama/gpu`, amending § 8's renderer line, with a row as KR-25 and KR-26 have; (2) say whether its design lives in § 8 as theirs do, or in its own repository; (3) whether kyoten builds it as its first consumer, as it does KR-25 and KR-26 (kyoten's KYR-9). **Its name is `@kama/graphics`** (the owner, 2026-11-03), imported as `graphics` (`graphics::Mesh`); a path package of that name installs and runs on 0.9.823. It avoids the first-party names in use (`gpu`, `window`, `http`, `ui`, `tls`, `sodium`, `postgres`, `redis`), the peers' own packages (`gfx` in FFD and the-mallow-man, `render` in cosmic-forge, `view` in FFD) and kyoten's `render` module, and it says nothing about games or real time. **Repro:** none applies, as nothing is broken. On kama `9f601224` (0.9.831 source; 0.9.823 built here), no `@kama` package or KR row covers a scene, mesh or material library. Not yet filed upstream: for kama to rule. |
| KY-10 | BUG | open | **kama's agent guidance says to `cast<int32>` for `main`'s exit code, and `main` cannot return an `int32`.** `AGENTS.md`, as `kama agents print` writes it on 0.9.839 (kama `agents/AGENTS.md:85-86`), says to *"reach for `cast<int32>(…)` only where the value genuinely leaves the size domain, such as `main`'s exit code"*. Since 0.9.684 (kama `d0ffc06e`), `fn int32 main()` is refused: *"`main` returns the exit status in the platform's own type — write `fn uint8 main()` (the one byte Linux and macOS keep; `fn uint32 main()` on Windows) … narrow a computed status with `cast<uint8>(…)`, which traps if it does not fit, or `truncate<uint8>(…)` to keep its low bits"*. An agent that follows the guidance writes an exit path the compiler refuses. It is one clause, but it is in the file every kama project's agent reads first. Repro: `fn int32 main() { isize n = 3; return cast<int32>(n); }`, then `kama check`. Reproduced on 0.9.839, Windows 11, msys2 UCRT64. Not yet filed upstream. |
| KY-11 | GAP | open | **A module cannot say which sibling modules it may import, so a rule between public modules cannot be the compiler's.** kyoten's rule ([design/architecture.md](design/architecture.md) § Decided, 2026-11-04) is that an engine system never imports another system. `visibility` is a list on the *imported* module, and a module a consumer imports must be `public`, which opens it to every sibling as well. So nothing in `kama.json` lets a game import `audio` while refusing `render` the same import. Repro: a library `eng` with modules `audio`, `render` and `frame`, and a game that depends on it by path and imports `eng::audio::play`. With `audio` `public`, `render`'s `import { eng::audio::play };` checks OK. With `"visibility": ["frame"]`, `render` is refused (*"module `eng::audio` is not visible from `eng::render` — its `visibility` in `kama.json` does not name this module"*), and so is the game (*"module `eng::audio` is not visible from `game`"*). **The ask:** a list on the importing node, naming the modules of its own package that it may import, so that `kama check` and the editor refuse a forbidden edge. One shape would be `"render": { "visibility": "public", "imports": ["frame", "world"] }`, but the shape is kama's. kyoten holds the rule meanwhile with a check in `tools/` (ROADMAP KYR-53). Reproduced on 0.9.840 (`0.9.840+g6cac55c7`), Windows 11, msys2 UCRT64. Not yet filed upstream. |
| KY-12 | GAP | open | **No job pool for CPU work, so a phase cannot hand out its parallel work cheaply.** kyoten's frame runs the subsystems of a phase in parallel wherever their stated access does not conflict ([design/frame-phases.md](design/frame-phases.md) § Decided, question 5). That means handing out work several times a frame. `parallel_for` spawns and joins its isolates on every call: 0.15 ms at 1 worker, 1.34–1.38 ms at 16, and 1.83 ms at 20 (measured on 0.9.793, [research/kama-for-engines.md](research/kama-for-engines.md) § 1). That is too slow for a barrier per phase. kama has already ruled the answer: KR-3's decision 5, *"a sized job pool for CPU work whose jobs may not park"*, which is step 9 of the fiber plan, while KR-3's next step is 7 (kama `docs/ROADMAP.md:86`, `6cac55c7`). KR-255 waits on the same step. **The ask (the owner, 2026-11-04):** raise step 9's priority. In the owner's words: *"we likely will need to get kama to put the pool as high priority"*. When kyoten first needs it is frame-phases question 7. Re-checked on 0.9.840 (`0.9.840+g6cac55c7`): `lib/std/concurrent/` holds no pool. The per-call cost was not re-measured, because a kama session was busy on this machine. For the owner to relay. Not yet filed upstream. **Extended 2026-11-04 (frame-phases question 6), on 0.9.845:** two more things the pool must do, or kyoten loses the compile-time proof where the performance is. **(1) Run borrowing work.** KR-3's decision 5 makes the pool's unit *"a `Sendable` job"* (kama `docs/design/fibers.md:285`), which is moved in, and a moved job cannot borrow the world's stores. kyoten's parallel work is proven by `scope` and `parallel_for` borrows, so the ask is that a `scope`'s children and a `parallel_for`'s workers run on the pool's threads, as Rayon's `scope` runs borrowing work on its pool. Otherwise kyoten could use the pool only through `UnsafePtr`. **(2) Hand out work without a heap allocation per call.** `@noheap fn void step(ref DynamicArray<int32> xs) { parallel_for (ref int32 e in xs, workers: cpuCount()) { e = e + 1; } }` is refused: *"heap allocation (parallel_for heaps a per-worker argument bundle) is forbidden here — this code is `@noheap`"*. The owner wants allocation up front, or at least very controlled (VISION, 2026-11-04, budgets), and `@noheap` is how kama proves a step keeps to it. |
| KY-13 | GAP | open | **A `spawn` takes exactly one argument, so a system over two stores cannot be its own parallel task.** In a world's own method, `spawn integrate(p: ref this.pos, v: ref this.vel);`, for `fn void integrate(ref DynamicArray<Pos> p, const ref DynamicArray<Vel> v)`, is refused: *"`spawn` entry `integrate` must take exactly one argument (the bundle)"*. kama states the rule: *"one parameter because the bundle *is* the boundary"* (kama `docs/SPEC.md:7274-7277`), so it is a gap, not a bug. **The workaround:** put the stores one task touches under one field (a `Motion` holding `pos` and `vel`, spawned as `ref this.motion`), which checks. But any other task on `vel`, even a reader, then overlaps all of `motion`, so the parallelism is coarser than the stated access. **Why kyoten cares:** nearly every system reads one store and writes another, and kyoten's parallel work is proven by the compiler ([design/frame-phases.md](design/frame-phases.md) § Decided, question 6). **The ask:** a spawn whose arguments are several places, each held to the prefix rule as if it were its own child; with KY-5, `const ref` arguments could then share. Reproduced on 0.9.845 (`0.9.845+gfd3ec5eb`), Windows 11, msys2 UCRT64. For the owner to relay. Not yet filed upstream. |
| KY-14 | GAP | open | **A boxed contract cannot be narrowed back to its concrete type, except an `Error`, and then only as a copy.** Type erasure itself works: with `type contract Column for resource { fn isize length(); }` and `type resource Store<T> implements Column { DynamicArray<T> items; … }`, a `DynamicArray<Owned<Column>> cols` holds `new Store::<Pos>.make()`, and `cols[0].length()` dispatches. The way back does not: `Optional<Store<Pos>> back = cols[0].as<Store<Pos>>();` is refused, *"`.as<T>()` applies to a boxed error (an `Owned<Error>`/`Shared<Error>` or a borrowed `Error`) — its static type isn't a poly-dispatch contract"*. On an `Error`, `.as<T>()` answers a copy and refuses a type that owns memory (kama `docs/SPEC.md:6986-6993`, xfail `as_downcast_uncopyable`), so a store could not come back even there. **Why kyoten cares:** storage whose component types are chosen at run time needs a typed way back from an erased column. That covers an archetype ECS (components option C), an editor's inspector, mods, and the project database loading a type the engine never named. Today it takes `UnsafePtr` and hand-rolled type ids, outside kama's checks. **The ask:** `.as<T>()` on any boxed contract, answering a borrow (`ref` or `const ref`) rather than a copy. Wanted whether or not kyoten picks option C (the owner, 2026-11-04). Reproduced on 0.9.845, Windows 11, msys2 UCRT64. For the owner to relay. Not yet filed upstream. |
| KY-15 | GAP | open | **Parallel tasks cannot take parts of a container chosen at run time, even distinct ones.** With `DynamicArray<DynamicArray<Pos>> cols` holding two columns, `scope { spawn step(col: ref cols[0]); spawn step(col: ref cols[1]); }` is refused at both spawns: *"An element (`a[i]`) or a call result names no place a static disjointness rule can pin — split a buffer with `parallel_for` instead"*. That is by design (kama `docs/SPEC.md:7477-7480`), and `parallel_for` covers an even split of one buffer, not a chosen part per task. **Why kyoten cares:** a scheduler that decides at run time which columns, zones or chunks each task gets. That covers option C's columns, and also option B's groups when load or region picks them. **The ask:** a split whose parts are proven distinct when it runs, as Rust's `get_disjoint_mut` does for a slice, and whose parts are places a `spawn` may borrow. Safe, with the check at run time instead of compile time. Wanted whether or not kyoten picks option C (the owner, 2026-11-04). Reproduced on 0.9.845, Windows 11, msys2 UCRT64. For the owner to relay. Not yet filed upstream. |
| KY-16 | GAP | open | **std's `PriorityQueue` cannot be serialized, deserialized or iterated, so a world holding one cannot be saved.** With `@generate(Serializable, Deserializable) type value Timer implements Comparable<This> { @field public int64 step; @field public int64 seq; … }`, a `@generate(Serializable, Deserializable) type resource Timers { @field PriorityQueue<Timer> due; … }` is refused twice: *"field `due` has type `PriorityQueue`, which cannot be serialized — a composite field is written through its OWN `serialize`, and `PriorityQueue` has none"*, and the same for `deserialize`. It is not `Iterable` either (*"Iteration order isn't meaningful for a heap, so it isn't `Iterable`"*, kama `lib/std/collections/priority_queue.kama:16-17`), so a world hash cannot fold it without draining it. Its own doc names it *"the fit for … event/timer scheduling"*. **Why kyoten cares:** a wait is a deadline held in the world, in a queue that is saved, hashed and rolled back with it ([design/frame-phases.md](design/frame-phases.md) § Decided, question 9). **The workaround:** kyoten keeps its heap in its own array. **The ask:** `Serializable`/`Deserializable` for `PriorityQueue` when its element is, writing the backing array in its stored order so a round trip is exact, plus a read-only view of that array for hashing. Reproduced on 0.9.845, Windows 11, msys2 UCRT64. For the owner to relay. Not yet filed upstream. |
