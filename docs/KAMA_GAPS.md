# kama gaps and bugs

The running list of what kyoten hits in [kama](../../kama). Two kinds of entry:

- **BUG**: kama does something wrong. Each entry carries a repro, and these should be fixed upstream.
- **GAP**: kama does not do something yet. Some gaps belong upstream; some are ours to build.

**Status values:** `open` · `worked-around` (we ship a local fix; upstream is still open) · `not kama's` ·
`wontfix`. There is no `fixed`: a fixed entry is deleted from this file, and the commit that deletes it says
which kama version closed it.

**Verify by running a repro, never by reading a version string.** Each entry names the kama version it was
reproduced on.

Built against kama **0.9.803** (seeded 2026-11-01; KY-2 to KY-7 found on 0.9.803). Re-checked on **0.9.810**

| KY-2 | GAP | open | **No Android target.** `kama transpile hello.kama --target ANDROID` answers *"unknown target 'ANDROID' (expected EMBEDDED\|HOST\|LINUX\|MACOS\|WASM\|WINDOWS, or an <arch>-<os>-<abi> triple)"*. The bare triple `aarch64-linux-android` transpiles and derives `OS_LINUX`, `ABI_ANDROID` and `HOSTED`, so std treats bionic as Linux, which nothing has exercised. A shippable build needs more than the triple: the NDK's clang and sysroot as a target entry, a shared library entered through `android_main` (a native activity) rather than `main`, the activity lifecycle (pause, resume, a lost surface), and APK/AAB packaging and signing. **Meta Quest's native route (OpenXR) runs on Android**, so kyoten's VR needs this ([design/xr.md](design/xr.md) question 4). Repro: a `println` hello, transpiled for each spelling, with a `@compileFor` probe per flag. Reproduced on 0.9.803, Windows 11; no NDK on this machine, so no link was tried. Filed upstream as kama KR-280 (`cd549777`). **Upstream since** (kama `4f0ecbdc`, 2026-11-01; not re-checked from here): KR-280 is in kama's NOW, measured with NDK r30 on this machine. A `kama.json` target carrying `--target=aarch64-linux-android29` builds an executable and a `.so`, and every std fixture that applies links once `-lpthread` is dropped. On the SDK's emulator, on this machine, 110 of those 135 pass on arm64 and x86_64 alike (kama `a23f1da2`, 2026-11-02); nothing has run on a headset. kama also filed KR-282 (an NDK wrapper is handed `-target`) and KR-283 (an installable APK), and its Windows machine claimed KR-280, KR-282 and KR-283 on 2026-11-02 (`62322f93`). It ruled XR kyoten's, so this target is what kama owes XR. **Ruled for production** (`1c1f165f`, 2026-11-02): kama finds the NDK itself (`$ANDROID_NDK_HOME`, else `$ANDROID_HOME/ndk/`), so `--target aarch64-linux-android29` builds with no `kama.json` target; `kama build` makes the signed APK; and `main` stays the entry on every target, with the lifecycle as events. |
| KY-3 | GAP | open | **No iOS target.** `--target IOS` is refused as `ANDROID` is. `aarch64-ios-none` transpiles and derives `OS_IOS`, so std's `OS_MACOS` declarations (`std::net`'s `ListenOptions`, for one) fall to their generic branch, and since a triple's components are the only flags, nothing names what macOS and iOS share. **Apple's own spelling, `arm64-apple-ios`, derives `ARCH_ARM64` and `OS_APPLE`**: neither `ARCH_AARCH64` nor `OS_IOS` holds, a trap for a triple copied from Xcode. A shippable build also needs Apple's clang and the iOS SDK (so a Mac), an app entered through `UIApplicationMain` with frames from `CADisplayLink` (the OS owns the loop, as the browser does on wasm), and a signed `.app` with a provisioning profile. `dlopen` is barred there, so kama's planned hot reload is desktop-only (kama `docs/ROADMAP_DETAIL.md` § the hot-reload library). Reproduced on 0.9.803, Windows 11, by transpiling only; a build needs a Mac. Filed upstream as kama KR-281, with the spelling trap as KR-279, which also covers `aarch64-apple-darwin` on macOS (`cd549777`). KR-281 is done on a Mac, after KR-279, which kama's Windows machine claimed on 2026-11-02 (`62322f93`). **The spelling trap is fixed** (KR-279, 0.9.807; re-checked here on 0.9.810): `--target arm64-apple-ios` is refused with *"target triple 'arm64-apple-ios' has a vendor (`apple`) in the middle, as clang spells it; kama's triple is <arch>-<os>-<abi> — write `aarch64-ios-none`"*, and `aarch64-ios-none` still transpiles. The iOS target itself (KR-281) is still open. |
| KY-5 | GAP | open | **Two `spawn`s in one `scope` cannot share a read-only borrow.** `fn void reader(const ref DynamicArray<int32> c)`, spawned twice as `spawn reader(c: ref c)`, is refused: *"two children in this `scope` borrow overlapping places (`c` and `c`) — a shared mutable borrow across tasks would race"*, with a second error calling the second spawn a write. One such spawn builds and runs. `c: c` is refused ("pass … by `ref`"), and `c: const ref c` does not parse. This is what SPEC § Structured concurrency states ("so is the same local twice", `docs/SPEC.md:7356`), so it is a gap, not a bug; `parallel_for (const ref T e in coll)` is the only read-only sharing today. **Why kyoten cares:** several systems reading one component store at once is where Bevy, Unity's jobs and Unreal's Mass get much of their parallelism ([research/component-models.md](research/component-models.md) § 4, probe 4). Without it, each parallel system in a phase must own a disjoint store. Reproduced on 0.9.803, Windows 11, msys2 UCRT64. Filed upstream as kama KR-288, unscoped: scheduled, design first, on what makes a type safe to read from several tasks (`1c1f165f`, 2026-11-02). |
| KY-6 | GAP | open | **A `--release --target WASM` build does not run Closure.** kama's wasm release passes `-Oz` and section GC (`src/kama.driver.cpp:13348-13351`) but never `--closure=1`, while emdawnwebgpu's README says *"In all cases, it is important to enable Closure to reduce code size in release"*. On kama's `examples/webgpu` triangle (brotli -q 11), `--closure=1` takes the JS from 11,768 to 7,117 B and the whole build from 22,518 to 17,867 B, and the triangle still draws the same pixels ([research/web-baseline.md](research/web-baseline.md)). A project can opt in today with an `ldflags` entry gated to `ARCH_WASM32`, so this is about the default, and about documenting that Closure renames a `jsLibraries` file's unquoted property names. Reproduced on 0.9.803 with emscripten 6.0.13, Windows 11. Filed upstream as kama KR-289, queued and unclaimed; the project-level `ldflags` opt-in stays the workaround (`1c1f165f`, 2026-11-02). |
| KY-9 | GAP | open | **A general-purpose graphics library as a first-party `@kama` package, where kama's roadmap keeps the renderer in the engine.** The owner wants kyoten's Three.js-shaped graphics library to be a `@kama` package (2026-11-03): scene, meshes, materials, lights, a camera and loaders, on `@kama/gpu`, naming no engine concept. In the owner's words: "If it can exist outside of kyoten it probably will be in kama for now. I can see the light weight graphics library used by just about anything and doesn't need to be game engine / simulation or even real time" ([design/architecture.md](design/architecture.md) § Decided, question 7). **What kama says today:** its § 8 engine track lists "scene/material" as a tier of the engine and says "the engine *spine* (buffer/pipeline/binding libraries, renderer) is the engine product" (`docs/ROADMAP_DETAIL.md:2843-2844`). With KR-25 and KR-26 claimed: "What stays in the engine is what the designs already leave out of them: frame pacing, the renderer and the XR swapchain" (`:2862-2863`). `@kama/gpu`'s scope keeps buffers, bindings and pipelines "*as an engine renderer*" out (`:2900-2901`). **Why the owner reads it as first-party:** kama's own rule is "a first-party package if it stands alone" (`:2865-2867`). GPU and window passed that rule because "a tool or an editor needs both as much as a game does", and the same holds here. cosmic-forge's viewer (its `render` package, which forge shaped as a renderer package for kyoten), kyoten's editor and the owner's non-game Three.js-style products would use it, and none needs a frame loop or a simulation. **The ask, for kama to rule:** (1) accept the library as a first-party package beside `@kama/gpu`, amending § 8's renderer line, with a row as KR-25 and KR-26 have; (2) say whether its design lives in § 8 as theirs do, or in its own repository; (3) whether kyoten builds it as its first consumer, as it does KR-25 and KR-26 (kyoten's KYR-9). **Its name is the owner's, not yet chosen.** It should not collide with first-party names in use (`gpu`, `window`, `http`, `ui`, `tls`, `sodium`, `postgres`, `redis`), the peers' own packages (`gfx` in FFD and the-mallow-man, `render` in cosmic-forge, `view` in FFD) or kyoten's `render` module. **Repro:** none applies, as nothing is broken. On kama `9f601224` (0.9.831 source; 0.9.823 built here), no `@kama` package or KR row covers a scene, mesh or material library. Not yet filed upstream: for kama to rule. |
