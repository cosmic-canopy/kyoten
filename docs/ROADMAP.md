# kyoten roadmap

**The order of work, and nothing else.** One row per item, a one-line summary, and a link to its reasoning.

Ids are `KYR-<n>`, permanent, never reused or renumbered. **Next id: KYR-65**

**Everything the vision asks for has a row, at the owner's request (2026-11-01),** so this file is the record of what is
wanted, including what is far off. A row past NOW is a place in the order, not a decision. Its design questions are
decided when the row comes up, in the doc it links. friendly-fire-department and the-mallow-man ship on their own
engines, so nothing here gates either one ([design/architecture.md](design/architecture.md)).

**The gate: when KYR-12 passes, a game can start on kyoten.**

| KYR-7 | **The component model, first version**, as KYR-1 decides it. Question 1 (2026-11-05): records generate the world as plain kama (B built on A), and the game writes system bodies whose signatures are their access. Storage is a table per (zone, prefab) of fixed-size value chunks, allocated when the zone loads, plus side stores (sparse sets) for components gained at run time. So this row holds the generator (in `tools/`, mapping its errors back to the records), the table, chunk, side-store and handle types, and the fusing of one table's non-conflicting systems into one pass per chunk. Its input format is components question 5, with project-database question 11. Question 6 (2026-11-05) adds budget records per scope with a ceiling on every store, reserved up front or committed chunk by chunk as an opt-in; refusal when full, with eviction as an opt-in; N chosen per archetype from a 16 KiB target; the footprint report per scope; and the 32 KiB frame guard in the engine's and every example's manifest, on every arm but Windows. Question 8, in part (2026-11-06): the generator resolves required components when it makes an archetype, adds those with defaults, refuses a prefab that lacks one without, and reports where each component came from, which a query answers (KYR-25). Scenes, zones and layers (2026-11-06): tables per (zone, layer, prefab), and in this slice one scene, one zone, one layer and one group, enough for the hello cube; streaming is KYR-61. Question 8, part a (2026-11-06): kyoten's own handle, 8 bytes (a 32-bit slot and a 32-bit generation) on every platform, a lookup answering here, gone or unloaded, and placed names resolved to handles when a zone loads, keyed by a 64-bit hash checked for collisions. Question 8 part b, in part (2026-11-07): the generator reads only the functions system records name, takes each parameter's mode and type from the compiler (KY-24 until `kama query` reports modes; reading the signature line itself meanwhile), gives each parameter the meaning its type has and refuses any other, and passes the step's time as `const ref Time`. Its output is split into files by archetype and phase and not committed (2026-11-07), so a kyoten command runs the generator before a build or a check (KY-28 asks kama for a manifest step). Systems are free functions named by their kama path, and a world component (formerly a singleton) is injected as a parameter. Then the vocabulary: a module (engine or game) is one kama module whose record sets a default rate, a system is now a processor, and the generator refuses a module `static` in a game. What a processor takes is decided (REFERENCE § What a processor takes), with typed queues that add with `.add(…)` (`Create<P>`, `Destroy`, `Gain<C>`, `Lose<C>`, `Send<C>`) and random keys derived by `nth(n:)`. Records are strict JSON read as the engine's kama types: the generator and the loader read every `*.records.json`, beside the code in `src/<module>/` or under `content/` (2026-11-07). Content records (2026-11-07): the app, prefabs with variants written `from`, bindings, and scenes as folders, with `main` the engine's default layer. The naming rule (2026-11-07): a module's generated names in a git-ignored `*.generated.kama` beside its code, which the generator clears of what it did not write; generated types with a suffix for their kind (`FireRandomKeys`, `BulletPrefab`); a prefab's component keys are type names, bare where unique, read through a field per spelling; names that become fields are identifiers, unique per kind across the game; a create queue creates its prefab's family (the prefab and its variants with the same components), chosen by data through a generated `<Prefab>PrefabId`, and a variant without a budget of its own lives in its base's table. The day-one engine components (2026-11-07): Transform on std::math with a quaternion, Mesh, Material, Camera, Light and Actions, and the world components Time and Environment. Coordinates (question 9, 2026-11-07): a Transform holds a zone and a `float32` offset from its centre, rebased exactly at the end of the phase with whole-metre zones; Y up, right-handed, metres | [components.md](design/components.md) |
